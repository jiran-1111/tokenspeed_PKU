# 真实模型输入的GDN独立递推对照

## 参考语义勘误（后续源码审计）

本文件下方是旧clamp归一化参考的真实结果，保留不覆盖。后续确认生产Prefill/Decode与固定HF使用平方和加epsilon，而旧oracle采用平方和clamp；二者并非完全相同语义，旧“相同精度语义”解释需收窄。对同一已有输入按加epsilon CPU FP64只读重算，输出/state relative-L2约3.615e-7/1.214e-7，两项原模块包络通过；详见[归一化参考审计](homework1_gdn_reference_audit_20261014.md)。新结果尚无独占二进制归档，不升级为最终验收；旧脚本、向量及全模型失败全部保留。

## 目的与协议

继续使用原工程合同，不修改1%全模型门槛或生产计算。对已捕获的真实0.8B layer0 GDN输入，验证默认生产路径的core输出及FP32最终state；不是此前临时HF边界兼容组合，也不是再次采集模型。

输入来自`results/raw/homework1_gdn_replay_20261014/`的engine conv、g、beta，包含128 tokens、16 heads、K/V维128；conv为BF16量化结果，g与beta为FP32。读取时逐文件校验已有manifest SHA，保持完全相同输入、零初态和scale。独立CPU逐token实现归一化、衰减、delta更新及输出，以FP32和FP64两种精度计算；递推内部state[K,V]，返回时转[V,K]对齐NPU池。FP32/FP64均从同一量化输入开始。

这里将捕获的g/beta作为递推输入，不重新验证其上游投影、卷积或门控计算，也不能从core通过推出完整模型通过。

FP64是数值参考，不是声称训练精度或服务精度为FP64。CPU只做离线参考，不是CPU serving fallback，未替代NPU权重/Prefill/Decode。代码位于`.tmp/homework1_gdn_trained_oracle_20261014.py`，完整源及四个参考张量归档到新raw目录。

## 结果

| 对照 | max-abs | relative-L2 |
|---|---:|---:|
| NPU输出对未舍入CPU FP32 | 0.000602096 | 0.001714246 |
| NPU输出对CPU FP32后BF16舍入 | 0.000244141 | 0.000135075 |
| NPU输出对CPU FP64后BF16舍入 | 0.000244141 | 0.000134982 |
| NPU FP32 state对CPU FP32 | 0.0000137985 | 0.0000044380 |
| NPU FP32 state对CPU FP64 | 0.0000137150 | 0.0000044262 |
| CPU FP32输出对FP64 | 0.0000000724 | 0.0000002068 |
| CPU FP32 state对FP64 | 0.0000020595 | 0.0000003304 |

每个张量262144元素，全部finite。BF16输出以实测前已有`atol=0.002, rtol=0.02`验收，FP32 state以已有`atol=0.0003, rtol=0.01`验收；对两种参考的四项检查全部通过，没有新放宽判据。BF16舍入参考与NPU输出精确相等元素分别261238/261260，不能从相近norm推断逐位相等。

这记录了相同默认输入下core/state与独立高精度递推的接近程度，但旧clamp归一化与生产加eps不完全同义，不能当作完全相同数学定义的对照；后续勘误与同输入核对见上文。前面engine/HF模块差异不能仅凭两者相差就认定递推错误，还需考虑归一化、beta和融合边界的不同舍入。只覆盖一个真实Prefill样例，不能外推全部18层、任意长序列或连续Decode；随机边界/多步/隔离仍需结合原测试参考语义限制解读。
